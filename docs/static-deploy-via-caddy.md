# Static deploy via Caddy (drop Netlify)

**Goal:** stop publishing static (Vite) apps to Netlify — we hit the free-tier
limit — and instead serve them from **our own KSA server**, reusing the exact
Caddy + `*.apps.etlaq.sa` mechanism the full-stack runtime already uses.

This is a *narrower* fix than "replace Netlify with a PaaS": full-stack apps
already run in-KSA (`lib/deploy/ksa.ts`). Only the **static** path still leaves
KSA (Netlify). Serving static from Caddy removes the limit **and** closes our
last non-KSA hosting path (PDPL win — see `deploy-and-server-setup.md`).

> **We are NOT installing Coolify.** The IP `149.104.105.231` is the existing
> production VM already running Caddy on 80/443 (`build/auth/id.etlaq.sa` +
> `*.apps.etlaq.sa`). A second reverse proxy would collide and duplicate the
> runtime we already have. Reuse, don't rebuild.

---

## How it works (mirror the full-stack path, minus the container)

Full-stack today (`lib/deploy/ksa.ts`): source → build container → long-lived
container on `127.0.0.1:<port>` → Caddy `reverse_proxy`.

Static is the same shape but simpler — **there is no server to run**, just files:

```
1. build   → in the sandbox: `npm run build`  (already how Netlify path builds)
2. pull    → read dist/ out of the sandbox
3. place   → write dist/ to  /opt/etlaq-apps/<slug>/public   (host, uid 1001)
4. route   → write /etc/caddy/apps.d/<slug>.caddy  with file_server + SPA fallback
             (existing systemd path unit reloads Caddy; TLS via HTTP-01)
→ https://<slug>.apps.etlaq.sa
```

Same slug convention as full-stack (`resolveSlug` in `ksa.ts`), so a project
keeps one stable subdomain and static/full-stack apps never collide (slug
carries the project-id suffix).

The Caddy vhost for static (vs. `reverse_proxy 127.0.0.1:<port>` for full-stack):

```caddy
# generated by Etlaq — do not edit; redeploys overwrite this file
<slug>.apps.etlaq.sa {
	encode gzip
	root * /opt/etlaq-apps/<slug>/public
	try_files {path} /index.html   # SPA fallback (replaces Netlify _redirects)
	file_server
}
```

## Part A — Code changes

### A1. New deployer: `lib/deploy/ksa-static.ts`
Model it on `netlify.ts` (build step) + `ksa.ts` (host/Caddy plumbing). Export:

```ts
runKsaStaticDeploy(provider, {
  projectId, siteName, prevUrl, // → slug via the same resolveSlug logic
}): Promise<{ url, slug, state }>
```

Steps inside:
1. `await provider.runShell('npm run build')` — reuse the sandbox build (same as
   `netlify.ts` step 1). Fail loudly on non-zero.
2. Pull the built output out of the sandbox. Simplest: reuse Netlify's trick —
   `cd dist && zip -r /tmp/site.zip .`, `readBinaryFileBase64`, then unzip on the
   host into `KSA_APPS_DIR/<slug>/public`. (Or read `dist/**` file-by-file; zip
   is fewer round-trips.)
3. Write the files under `KSA_APPS_DIR/<slug>/public` using the **same
   `safeJoin` guard** as `ksa.ts` so no tenant path escapes the dir. Clear the
   old `public/` first (static has no caches worth preserving — unlike the
   full-stack `PRESERVED` set).
4. Write `KSA_CADDY_APPS_DIR/<slug>.caddy` with the `file_server` block above
   (factor `writeCaddyRoute` in `ksa.ts` to take a body, or add a sibling
   `writeStaticCaddyRoute`).
5. Return `https://<slug>.apps.etlaq.sa`. No container, no port allocation, no
   HTTP probe needed — Caddy serves files directly.

Reuse from `ksa.ts` (extract to a shared `lib/deploy/ksa-shared.ts` if cleaner):
`slugify`, `resolveSlug`, `safeJoin`, the Caddy-dir write. **No new npm deps.**

### A2. Wire the route: `app/api/deploy/route.ts`
Replace the Netlify branch (the `// --- static` block, ~L120–148) with a call to
`runKsaStaticDeploy`. Keep the **shape** of the response identical
(`success/target/url/state/message`) so the UI needs no change.

Keep Netlify as an **escape hatch**, mirroring the existing
`FULLSTACK_TARGET=vercel` pattern:

```ts
if (process.env.STATIC_TARGET === 'netlify') { /* existing runNetlifyDeploy path */ }
else { /* new runKsaStaticDeploy path (default) */ }
```

Persist `deployUrl` + `deployTarget: 'static'` as today. `netlifySiteId` is only
written on the Netlify branch — leave the column, just stop populating it on the
default path.

### A3. Leave `detect.ts` alone
`detectDeployTarget` still returns `'static'` for a plain Vite SPA — routing is
unchanged; only the static *target* moves.

## Part B — Host prerequisites (on 149.104.105.231)

Most of this already exists from the full-stack runtime. Deltas:

- **DNS** — `*.apps.etlaq.sa → 149.104.105.231` — **already added.** ✅
- **Static dir** — `/opt/etlaq-apps/<slug>/public` is created per-deploy by the
  code (writes as uid 1001, same as full-stack). Nothing to pre-provision beyond
  `/opt/etlaq-apps` already existing.
- **Caddy read access** — Caddy must be able to *read* the static files. The
  full-stack path only needs Caddy to proxy a port, so verify Caddy's user can
  read `/opt/etlaq-apps/<slug>/public` (files are uid 1001). If Caddy runs as a
  different user, make the tree group- or world-readable (`0755` dirs / `0644`
  files — the writer should set these).
- **Caddy import** — `import /etc/caddy/apps.d/*.caddy` + the `caddy-apps.path`
  systemd watcher **already exist** (full-stack uses them). Static `.caddy` files
  drop into the same dir and reload the same way. ✅
- **TLS** — per-subdomain HTTP-01, already automatic for `*.apps.etlaq.sa`. ✅

No new ports, no new services, no Coolify.

## Notes / decisions still open

- **Redeploy overwrite vs. atomic swap.** Writing straight into `public/` means a
  brief window mid-deploy where files are partial. For a static SPA it's
  seconds; if it matters later, write to `public.next/` then rename.
- **Old Netlify sites.** Existing `projects.netlifySiteId` rows keep working on
  Netlify until each is re-published (which moves them to Caddy). No migration
  needed; optionally sweep/delete Netlify sites later to free the account.
